# 用户配置只读，运行期配置只走命令行覆盖

`~/.codex/config.toml` 由用户所有，Codey 不写入、不迁移、不重写，也不做"自动修复"。本次运行需要的配置一律通过 `-c key=value` 传给单次 Codex 进程；主进程补丁把同一批覆盖打进 `NODE_OPTIONS=--require` 脚本，同样不落盘。

Hook 定义和信任状态通过单条 `-c 'hooks={…}'` 运行期覆盖传入，信任键使用 `/<session-flags>/config.toml:<事件>:<组索引>:<处理器索引>`。用户的 `hooks.json` 及其信任项由 Codex 合并加载，Codey 不写入或备份该文件。旧版已写入的 Hook 只通过原有租约恢复路径清理一次。

这条约束由三层验证守护，缺一不可：完整启动退出后 `config.toml` 字节级不变，证明最终状态；把 `config.toml` 设为只读权限后完整启停仍然成功，证明运行期从未写入；以及对启动、启动失败清理、重启、退出、旧租约恢复五条生产路径的写入调用审计。只有第一层会漏掉"先写入再恢复"的实现。

## 后果

放弃上游的 `codey_router` 恢复桩。v0.9.x 期间创建、`model_provider` 被标记为 `codey_router` 的旧会话，需要一次显式迁移——改写会话库与 rollout 记录，不碰用户配置。控制台提供该入口；启动时不再自动改写会话归属，这些旧会话在迁移前不能当普通会话继续使用。

## 2026-10-05 描述修订

原文“同样不落盘”不准确。运行期覆盖不会写入 Codex 的 `config.toml`，但同一份覆盖列表会保存在 Codey 自有目录的私有启动载体中，供本次启动使用：`startup-require` 脚本、macOS 包装脚本和 Windows 的 `codex-cli-launch.json`。脚本保留及租约失效规则见[内部开发文档](../../INTERNAL_DEVELOPMENT.md#启动与退出)。本修订只更正载体描述，不改变用户配置只读的决策。

## 2026-10-27 收窄修订

控制台要管理 MCP 与 Skill、检查并修复 Codex 配置、切换多个官方账号，这些操作必须写 Codex 目录中用户拥有的文件。因此把"永不写入"收窄为"生命周期内不写入"，其余决定不变。

- 启动、重启、退出、启动失败清理和旧租约恢复，仍然绝不写 Codex 目录中用户拥有的文件：`config.toml`、项目配置、Skill 目录、`auth.json`。上文三层验证继续守护这五条路径。
- 只有用户在控制台的显式操作可以写这些文件：MCP 与 Skill 的增、删、改、导入，配置检查与修复，切换官方账号。每次写入前备份原文件，写入后校验结果。
- 既有的"手动修复插件市场"也属于显式操作。它通过运行组件的配置管理器写 `config.toml`：写入前校验新文档，并轮换保留最多 5 份 `config.toml.bak`，满足写前备份。
- 启动时唯一允许的同步方向，是把 Codex 刷新后的 `auth.json` 抄回 Codey 自己的账号库。启动时不写 `auth.json`。
- 切换渠道只用运行期覆盖，不写 `config.toml`。
